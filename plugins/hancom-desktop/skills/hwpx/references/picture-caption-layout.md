# 사진과 캡션 배치

짧은 사진 설명 정리 요청에서는 기존 사진·캡션 내용, 그림 데이터와 연결, 표시 크기와 비율을 보존한다. 사진마다 native 캡션을 붙이고 본문과 구별되는 간격을 둔다. 내용이나 보고서 구성을 의무화하지 않는다.

## 좁은 사진 아래 긴 설명

한컴의 위·아래 캡션은 개체 폭을 따른다. Caption.Width만 크게 설정해도 아래 캡션 폭이 늘어나지 않는다. 공식 ‘여백 부분까지 너비 확대’(Caption.CapFullSize=1)를 사용하고, 명시한 설명 영역 폭과 그림 폭의 차이를 개체 좌우 바깥 여백으로 배분한다. 새 단독 사진 문단은 좌우에 균등 배분할 수 있지만 기존 앵커는 주변 문맥에 맞게 보존한다. 확장 영역은 실제 열/본문의 사용 가능 폭을 넘기지 않도록 사전에 확인한다.

COM 시험에서는 정확한 그림 ID를 선택·재확인하고 ShapeObjDialog의 기본 속성에서 OutsideMarginLeft/Right/Top/Bottom을 조정했다. 중첩 ShapeCaption(Caption)은 Side=3, Gap=850, CapFullSize=1을 사용했다. TextWrap=1은 위아래 배치이다. Gap 약3mm, 위아래 바깥 여백 약4mm는 시험 시작값이며 문서에 따라 조정한다. 그림 너비·높이를 캡션 때문에 바꾸지 않는다.

사진 바로 앞 소제목이 이전 쪽에 남으면 그 소제목에만 keep_with_next를 적용하고 다시 출력한다. 모든 본문을 무조건 묶지 않는다. 새 사진은 단독 글자처럼 취급 문단에 넣고 native 캡션으로 연결하는 방식을 우선 검토한다.

## 확인과 지원 범위

사진 바이트·연결·표시 프레임·비율, 캡션 및 본문 전체 텍스트·사용 서식을 대조한다. Native 속성 편집에서 imgDim/imgClip의 단위가 바뀔 수 있다. 양쪽 모두 정확한 전체 이미지이고 새 좌표가 실제 래스터 치수와 일치함을 별도로 입증한 경우만 표현 정규화로 기록한다. 실제 자르기 변화를 무시하거나 완료 게이트를 완화하지 않는다.

열기→저장→재열기→PDF를 실행한 뒤 모든 쪽에서 각 사진과 전체 캡션, 앞 소제목과 후속 본문, 간격·겹침·잘림을 확인한다. COM 생성과 보안 모듈 등록은 별도 영수증 항목으로 확인한다. 보안·레지스트리·DLL 설정은 변경하지 않는다.

HWP006에서 기존 다단 세로 사진(설명 영역64mm), 새 다중 사진 및 별도 쪽 경계 문서(140mm 설명 영역)를 실제 한글2024에서 검증했다. 사진 선택 COM 실험은 고정 입력 전용 프로젝트 worker이며 범용 편집 CLI로 배포하지 않았다. 그룹·이미 자른 그림·표 안 그림·임의 앵커 재배치는 아직 미검증이다. 과거 HWP005 범용 contain 및 차트 OLE 보존 실패는 해결됐다고 간주하지 않는다.

공식 근거: https://help.hancom.com/hoffice130/ko-KR/Hwp/table/tableattribute/table(outblank).htm 및 프로젝트 보관 ParameterSetTable_2504 Caption/ShapeObject 정의.


## 설명문이 사진 설명처럼 읽히도록

사진 캡션은 이미지에서 무엇을 봐야 하는지 구체적인 위치·대상·상태를 짧게 짚는다. 예: “그림 1. 출입문 오른쪽에 쌓인 상자와 왼쪽 통행 공간”. 사진으로 알 수 없는 촬영 시점·치수·원인·법적 적합성은 추측하지 않는다. 긴 분석·제안·주의사항은 인접 본문에 분리한다. 합성/출처 표시는 짧게 명시하되 모든 캡션을 긴 주의문으로 채우지 않는다.

본문보다 작은 캡션 글씨와 사진 가까운 간격, 해당 사진과 맞는 설명 폭을 선택한다. 시험에서는 150mm 가로 사진 아래 9pt 회색 한 줄 캡션, 약2mm 간격과 별도 해석 본문을 사용했다. 이것은 참고안이고 모든 캡션의 한 줄/중앙 정렬/회색을 의무화하지 않는다. 설명이 길면 필요한 내용을 유지하고 적절한 줄바꿈·폭을 검토한다.

HWP006 후속 합성 장면 1쪽을 실제 한글에서 저장·재열기·PDF 전쪽 확인했다. 최초 writer 저장의 빈 텍스트/그림 내부 이름 정규화 strict 실패는 유지하고, 이미지 소비 위치·바이트·표시 프레임·전체 본문·활성 서식을 독립 대조한 native 저장본에서 새 완료 게이트를 통과했다. 다양한 실제 사진에 대한 일반 성능이나 독립 A/B 효과를 입증한 것은 아니다.


## 나란히 놓은 사진

전후 비교는 사진별 라벨과 native 캡션을 각각 연결하고 사진 윗선을 맞춘다. 설명의 길이가 다를 때 짧은 설명을 억지로 늘리지 않는다. 후속 본문은 두 설명 중 더 긴 캡션의 끝보다 아래에서 시작하도록 공간을 확보한다. 각 사진은 원비율로 표시하며 임의 자르기나 변형을 하지 않는다.

HWP006 후속 시험에서는 새 문서의 테두리 없는 1행2열 표를 배치 컨테이너로 사용했다. 각 셀은 위 정렬, 사진은 글자처럼 취급, 각각 아래 native 캡션을 가진다. 묶음이 한 쪽에 들어갈 크기인 경우 표 나눔 TABLE과 앞 소제목의 다음 문단 연결을 선택하고 실제 쪽 이동을 확인한다. 거대한 묶음을 무조건 한 쪽에 유지시키지 않는다. 셀 높이는 긴 캡션에 필요한 높이를 포함해 설정하고 잘림을 실제 출력으로 확인한다.

두 가로 사진 각78mm, 왼쪽 한 줄·오른쪽 세 줄 캡션의 기본1쪽 및 별도 쪽 경계2쪽을 실제 한글2024 저장·재열기·PDF 전쪽 검토했다. 사진 바이트/연결/표시 크기/crop/비율과 전체 텍스트·활성 서식을 비교했고, 최종 엄격 완료 게이트도 통과했다. 사진 연결 순서 뒤바뀜은 읽기 전용 메모리 변조 대조에서 탐지했다. 최초 새 작성본 저장의 내부 이름/빈 텍스트 정규화 실패는 유지했다.

이 방식은 새 문서에서 시험한 선택 배치이며 기존 임의 표에 사진을 삽입하는 범용 CLI를 추가한 것은 아니다. 세로·가로 혼합 비율, 사진 교체 후 구조 유지, 사용자 실제 문서의 편집은 이번 시험에서 미검증이다. AI 정리 후 장면은 가상안으로 표시하고 실제 작업 완료로 서술하지 않는다.


## 가로·세로 사진을 함께 놓을 때

같은 폭을 억지로 적용하거나 임의 자르기보다 원비율을 유지하면서 높이·중앙 배치를 선택한다. HWP006 후속 새 문서 시험에서는 높이52mm, 가로78mm 및 세로 약34.67mm를 사용했다. 사진의 역할을 각각 짧은 라벨로 구분하고, 좁은 사진 설명 폭은 표시 사진의 폭과 별도로 설계했다.

테두리 없는1행2열 배치에서 각 설명 영역78mm, 좁은 그림의 좌우 바깥 여백을 균등 배분하고 native Caption.full_sz=True로 전체 설명 폭을 확보했다. 새 객체를 public 작성 API로 만들었고 기존 임의 표 안 그림의 수정 기능을 추가한 것은 아니다. 기본1쪽·별도 쪽 경계2쪽을 실제 한글 저장·재열기·PDF 전쪽 확인했다. 사진의 원본 바이트/연결/표시 프레임/imgRect/imgClip/imgDim과 전체 텍스트·활성 서식을 독립 비교했다.

PDF 이미지의 bbox는 native 원본 프레임과 출력 래스터 경계 차이가 있을 수 있다. 이번 측정에서 최대 약0.071mm 차이가 있었으며 HWPX 기하는 정확히 보존됐다. PDF에서는 독립 입력의 예상 물리 크기와 출력 픽셀 격자의2픽셀 한계 안인지 기록했다. 1% 너비 변형은 별도 부정 대조에서 거부됐다. 이런 측정 정밀도 보완으로 crop/그림 바이트/한글 프레임 보존이나 엄격 완료 게이트를 완화하지 않는다.

이 항목은 앞 병렬 시험의 ‘혼합 비율 미검증’ 중 위 두 비율의 새 문서 사례만 추가 확인한 것이다. 실제 사용자 문서·다른 비율·사진 교체 후 유지·임의 표 그림 편집은 계속 미검증이다. AI 장면은 합성이라고 표시하고 서로 다른 장면을 실제 전후 변화의 증거로 쓰지 않는다.
