# 한글 공식 블록 저장으로 부분 재사용

설치된 Windows 한글에서 긴 원본의 필요한 표·본문을 원래 모양으로 별도 HWPX에 남길 때 검토한다. 원본 전체를 새 주제로 채우거나 일부 속성으로 새 표를 재구성할 필요가 없다. 한글이 선택 영역의 저장을 처리하고, 나온 작은 파일은 기존 편집·검증 도구로 다룬다.

이미 확인한 블록은 [재사용 양식 목록](reusable-block-library.md)에서 선택한다. 추출을 매번 반복하지 않는다. 새 원본이나 바뀐 원본의 필요한 부분만 아래 순서로 등록한다.

## 선택과 실행

1. 현재 원본 해시와 필요한 문단·표 범위를 확인한다. 페이지 번호는 찾기 단서이며 표가 쪽 경계를 넘거나 문단 일부만 포함되는지 실제 한글에서 확인한다. 고정 문단 번호를 다른 파일이나 변경된 원본에 재사용하지 않는다.
2. [Windows 검증 스킬](../../hwpx-windows-finalize/SKILL.md)의 환경·보안 모듈·소유 프로세스 보호 절차를 재사용한다. COM에서 `SetPos`/`SelectText` 등 공식 선택 API를 쓰거나 한글 UI에서 범위를 선택한다. 저장 전에 실제 선택 내용과 원본의 선택 범위를 대조한다. 개체만 선택한 상태와 문서의 블록 선택을 구분한다.
3. 한글 UI의 **파일 → 블록 저장** 또는 공식 `FileSaveBlock_S` 액션으로 원본과 다른 신규 `.hwpx`에 저장한다. 이 액션의 `HFileOpenSave.filename`은 신규 경로, `Format`은 `HWPX`다. 원본을 저장하거나 삭제하지 않는다. 아래는 범위 확인 뒤 실행할 액션 조각이며, 환경·선택·종료 검사를 대체하는 독립 실행기는 아니다.

```text
HAction.GetDefault("FileSaveBlock_S", HParameterSet.HFileOpenSave.HSet)
HParameterSet.HFileOpenSave.filename = 새_파일_절대경로
HParameterSet.HFileOpenSave.Format = "HWPX"
HAction.Execute("FileSaveBlock_S", HParameterSet.HFileOpenSave.HSet)
```

4. 저장본을 다시 열고 실제 PDF를 출력한다. 선택한 원본 구역의 용지 방향·크기·여백도 대조한다. 뒤 구역에서 블록 저장한 가로 문제 분석지가 앞 구역의 세로 설정을 따라 오른쪽 열이 잘린 실제 사례가 있었다. 필요한 경우 공개 `doc.page.set_size`/`set_margins`로 선택 구역의 실제 HWPUNIT 값을 새 사본에 복원하고, 쪽 속성 외 내용·표·선·글자 서식 불변과 전체 출력을 확인한다. 방향 enum이나 여백을 문서마다 추정하지 않는다. 원본 선택 영역과 새 파일의 내용·표 크기/병합·글꼴·색·선·그림을 대조한다. 원본 해시 불변과 소유 프로세스 정상 종료도 확인한다. 새 파일 경로만 존재하거나 액션이 성공한 것만으로 완료하지 않는다.
5. 실제 요청의 내용은 그 작은 파일에 기존 선택 텍스트 또는 batch 편집 경로로 반영한다. 셀 안의 지정 run 수정과 단건 본문 치환을 혼동하지 않는다. 아래의 내용별 변형 경로를 선택하고 실제 출력으로 확인한다.

한글의 `GetTextFile("TEXT", "saveblock")`은 선택 대조용이며 서식을 저장하지 않는다. 숫자 문자 참조로 반환된 글머리표는 올바르게 해석해 비교하고, 차이를 무조건 무시하지 않는다. 데스크톱 `GetTextFile/SetTextFile`의 형식으로 `HWPX`를 넣는 방법은 공식 포럼에서 지원하지 않는다고 안내했다. HWPX는 파일로 블록 저장한다.

### 그룹 글상자 제목의 제한 편집

그룹 도형 속 목차 제목은 일반 본문 run 색인에 나타나지 않을 수 있다. 실제 시험에서는 공식 RepeatFind로 유일한 제목을 선택하고 InsertText로 바꿨을 때 끝의 빈 run 서식을 물려받아 글꼴·굵기가 달라졌다. 선택 전체의 CharShape는 혼합 속성을 생략하므로 그것만 읽어 원래 서식을 확보했다고 판단하지 않는다.

이 목차의 성공 경로는 원본 해시·선택 문구 확인 → GetSelectedPosBySet으로 정확한 범위 확보 → 같은 글자 모양인 제목의 첫 실제 글자만 선택해 CharShape 보관 → 원래 제목 전체를 다시 정확히 선택해 치환 → 새 제목을 재선택해 보관한 CharShape 적용 → 저장·재열기 후 글자 서식·그룹 개체·내용·출력 대조였다. 이 사례의 HY헤드라인M/굵게/22pt를 다른 제목에 강제하지 않는다. 여러 서식이 섞인 제목은 구간별 원래 서식 대응이 필요하다. 목차 항목/쪽수의 자동 갱신은 이 제목 편집 시험 범위가 아니다.

공식 참고: [CharShape의 선택 영역 속성 처리](https://developer.hancom.com/webhwp/devguide/hwpctrl/properties/charshape), [GetSelectedPosBySet의 범위 읽기](https://forum.developer.hancom.com/t/topic/1532). 실제 데스크톱 성공은 등록 목차 항목의 증거와 연결되어 있다.

## 조립과 지원 범위

비연속 여러 구역은 각각 저장한 뒤 공식 `InsertFile`을 검토할 수 있다. 준비된 단일 구역 블록은 [공통 compose](simple-entry.md#준비된-블록-조합)로 조합·저장·재열기·PDF 출력을 연결한다. 임의 범위를 추출하는 범용 CLI는 아니며, 다른 용지·방향·여백을 구역별로 유지하는 조합은 간편 경로의 지원 밖이다. 문서 조립은 새 대상의 편집 용지·번호·그림과 실제 출력을 확인해야 하며, 단일 블록 저장 성공으로 여러 원본 조합까지 보장하지 않는다.

2026-10-26, 한글 2024 13.0.0.653에서 실제 9쪽 운영계획의 한 문단(색·그림·가로/세로 병합이 있는 7행 4열 표)을 블록 저장했다. 결과는 1쪽이며 22개 셀의 위치·크기·안 여백·병합과 텍스트 순서가 원본과 같았다. 실제 PDF의 선택 영역 픽셀 비교도 같았다. 저장본의 두 문구를 기존 batch로 다시 수정해 한글 출력까지 확인했다. 이 시험만으로 다른 원본·PC·비연속 쪽 조립을 검증한 것은 아니다. 이후 세 블록·두 순서 조합의 실제 범위는 [재사용 양식 목록](reusable-block-library.md)에 기록했다.

## 내용에 맞게 변형하면서 디자인 유지

원본을 새 목적에 활용하는 요청에서는 행 수·셀 높이·열 배분·쪽수를 원본에 고정하지 않는다. 내용의 양과 관계에 맞춰 필요한 변경을 판단한다. 유지할 선의 굵기·종류·색, 배경, 글꼴과 명시적 필수 조건을 구분하고, 사용자가 디자인 변경도 허용했다면 그 범위에서 바꾼다. 작은 조정마다 별도 승인을 요구하지 않는다.

- 문구만 바꿀 때는 지정 run을 편집한다. 긴 내용은 필요한 칸 높이·열 배분·행 추가 또는 본문 분리를 검토한다. 원본 크기를 유지하려고 글자를 자동 축소하거나 내용을 생략하지 않는다.
- [표 크기](table-layout-edit.md), [양식 변형](form-adaptation.md), [여러 문단 표 편집](rich-table-edit.md)의 실제 지원 구조에 맞춰 선택한다. 병합표에 단순 표의 행 높이 알고리즘을 적용하거나 셀 전체를 새 기본 서식으로 쓰지 않는다.
- 선·배경을 의도적으로 바꿀 때는 [선·채우기](cell-borders-diagonals.md)의 검증된 경로를 쓴다. core 6.3.0의 `set_cell_shading`은 같은 배경색을 쓰는 서로 다른 테두리의 셀을 잘못 합치는 재현 사례가 있다. 변경할 속성만 바꾸고 기존 공유 서식 정의를 일괄 수정하지 않는다.
- 전후 대조는 서식 ID 번호만 보지 않고 각 셀이 실제 참조하는 선·채우기 정의, 글자·문단 서식과 의도한 크기를 읽는다. 높이 변경에 따른 인접 셀·병합 구역의 재배치와 실제 출력의 밀도·잘림도 확인한다. 내부 정의 재정렬 자체를 고치는 작업과 구분한다.

위 시험의 긴 문구는 기존 칸에서 빽빽해졌다. 별도 한글 공식 `TablePropertyDialog` 시험으로 정확한 문구가 있는 셀을 확인하고 현재 `ShapeTableCell.Height`에 2268 HWPUNIT(약 8mm)을 더했다. 현재 기본 속성을 먼저 읽고 높이만 변경했으며, 저장·재열기한 1쪽 전체에서 여유가 생겼다. 22개 셀의 실제 테두리/배경 정의·글자·문단 서식·안 여백·너비·병합과 그림이 유지됐다. 파일에 저장된 높이 11887과 한글이 배치한 높이 12000은 달랐으므로, 실행 시 실제 값을 읽고 대상·값을 대조해야 한다. 이 숫자나 셀 위치를 다른 원본의 기본값으로 쓰지 않는다.

이것은 해당 병합표의 제한된 높이 조정 시험이며 임의 표의 자동 맞춤·행 추가/삭제까지 검증한 것은 아니다. 범용 셀 높이 CLI를 추가하지 않았으며 기존 도구의 거부 범위를 해제하지 않는다. 공식 기능으로 별도 처리할 경우에도 새 사본과 정확한 대상 확인·서식 대조·실제 출력 검증을 연결한다.

저장 시 내부 정의 정규화 자체를 고치는 작업으로 확대하지 않는다. 눈에 보이는 결과·활성 서식·내용·필요한 편집 가능성을 확인하고, 내부 바이트 동일성과 구분한다.
