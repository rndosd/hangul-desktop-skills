# 파일 방식 차트 재작성 — 시험용 후보

사용자가 기존 차트와 비슷한 모양의 재생성을 허용하면, 원자료에 맞는 새 ChartML을 만들고 `doc.shapes.add_chart`로 native 차트를 작성할 수 있다. 화면 조작이나 한글 COM 편집 API는 필요하지 않다. 보고서 전체를 임의 재작성하거나 기존 차트의 색·축·폰트·위치가 모두 보존된다고 약속하지 않는다.

`scripts/chart_rebuild.py`는 함께 배포한 `assets/chart-rebuild/clustered-column.xml`의 해시를 고정한 두 계열 세로 묶은 막대 차트 생성기다. 일반 차트 편집기가 아니다. JSON에는 title과 matrix(머리글 1행, 이후 항목명/첫 계열/둘째 계열)를 넣는다. 중복 항목·계열, 빈 값, 비수치·비유한 수치, 열 개수 불일치, 40개 초과 항목, 다른 템플릿을 거부한다. 기존 출력은 덮어쓰지 않는다.

```powershell
& $pythonExe scripts/chart_rebuild.py --data assets/chart-rebuild/sample-data.json --output new-chart.xml
```

검토한 matrix로 원자료 표도 함께 작성한다. ChartML을 native 차트로 넣고 크기와 주변 간격을 정한다. 이번 시작값은 32250×18750 HWPUNIT, 글자처럼 취급, 상하 1134 HWPUNIT(약 4mm)이다. 고정 보고서 형식이나 의무 간격이 아니다. 새 개체 작성 코드에서만 설정하고, 기존 임의 개체를 이 경로로 변경하지 않는다.

실제 사용 전 원자료와 표·계열명·항목·모든 수치·개수·인덱스를 별도 대조한다. 필요한 한글 열기·저장·재열기·전체 PDF 출력은 동료 finalize의 기존 보호 도구로 검증한다. COM은 이 검증 단계에만 쓰이며, COM도 배제하면 native 검증은 수동으로 남는다. 데이터 편집 창의 후속 사용 가능 여부는 실제 확인 없이 완료로 보고하지 않는다. OLE 바이트 차이와 문서 사용 실패는 구분하며 아래 실무 전달 기준을 따른다.

검증 기록: HWP007-CHART-REBUILD-20261004. 두 합성 자료의 변경 전후 4개 파일은 표·ChartML/패키지 구조를 확인했다. 수치 999로 바꾼 반례는 거부했다. 이 후보의 native 결과는 해당 실행 보고서의 최신 상태를 읽는다. 원본에 대한 범용 차트 교체·복합 차트·다른 한글 버전은 미검증이다.


2026-10-05 후속: 한글2024 13.0.0.3903에서 변경 전후4파일의 열기/저장/재열기/PDF와 변경 후2파일의 반복 저장을 수행했다. 두 계열/모든 항목과 수치 유지, 출력4쪽 실제 검토, 표-차트 약9.39mm/차트-본문 약7.65mm 확인. 반복 저장의 Contents/Chart 파트와 PDF 픽셀은 동일하지만 OLE 호환 바이너리가 매번 달라 strict 완료 gate는 FAIL 유지. PDF에는 한글이 차트를 래스터로 출력하므로 PDF 이미지 유무를 HWPX native 차트 판정으로 쓰지 않는다. UI 데이터 편집 창 시험 및 임의 기존 문서 교체는 미검증이다.


## 완성한 파일을 확인하는 기본 경로

파일 작성기로 이미 HWPX를 완성했고 native 재저장이 필요한 요청/문제가 없다면 finalize의 기존 OpenOnly를 사용한다. 정확한 전달 후보를 열기·Clear 후 재열기·PDF 출력하고 source hash가 그대로인지 확인한다. 저장 시험이 필요한 경우는 SaveAs/새 사본/기존 strict gate를 실행하되 그 결과와 아래 실무 전달 판정을 분리한다.

2026-10-05 별도 OpenOnly 시험: 앞선 월별/창구별 변경 후 후보2개를 같은 고정 원자료로 확인했고 native 열기/재열기/PDF·전체2쪽 검토·원자료 표/ChartML·간격 확인을 완료했다. 입력 HWPX 전체 바이트가 그대로이며 OLE 바이너리가 새로 생기지 않았다. PDF의 차트 이미지는 한글의 출력 방식이며 HWPX는 native ChartML이다. 예전 SaveAs strict 실패는 그대로다. OpenOnly 성공을 native 데이터 편집 창이나 구형 OLE의 의미적 호환 검증으로 확대하지 않는다.

## 실무 전달 기준

사용자가 문서 생성과 실제 사용을 우선하고 OLE 바이트 동일성이나 구버전 호환성까지 요구하지 않으면, [finalize의 실무 차트 전달 기준](../../hwpx-windows-finalize/references/acceptance-policy.md#실무-차트-전달-기준)을 따른다. 내부 OLE 바이트 차이만으로 작업을 멈추거나 차트를 반복 재작성하지 않는다. 정상 생성·열기·필요한 저장/재열기·요청된 출력, 원자료와 내용·서식·배치 확인이 끝났으면 검증한 정확한 파일을 전달하고 OLE 차이는 짧은 경고/미검증 사항으로 남긴다. 파일 생성·내용·출력의 실제 실패는 수정한다. 기존 strict FAIL을 PASS로 덮어쓰거나 전체 OLE 의미 동등성을 확인했다고 말하지 않는다.
