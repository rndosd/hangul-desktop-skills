# 표 이외의 보고서 지면 선택

짧은 요청에서 설명·사진·그림·각주·부록이 필요한 보고서를 만들 때 읽는다. 아래 요소는 선택지다. 한 문서에 모두 넣거나 예시의 목차·쪽 수·주제를 따라야 하는 규칙이 아니다. 사용자가 준 기존 양식의 보호 영역과 내용 보존 조건을 우선한다.

## 내용에 따른 선택

| 내용의 역할 | 가능한 표현 | 함께 확인할 것 |
|---|---|---|
| 배경·원인·해석 | 문단과 소제목 | 표로 바꾸면서 논리 관계를 잃지 않는가 |
| 잠정 판단·중요 조건 | 짧은 요약 또는 강조 상자 | 미정 조건이 상자에서 빠지지 않는가 |
| 수치의 변화·비교 | 그래프와 해석 문단 | 단위·축·집계 정의·출처가 가까이 있는가 |
| 현장의 관찰 근거 | 사진·캡션·관찰 설명 | 실제 증빙인지 예시인지, 사진으로 확인 못 하는 판단을 단정했는가 |
| 순서가 핵심인 작업 | 간단한 절차도 또는 번호 목록 | 글자로도 순서를 읽을 수 있는가 |
| 반복 속성의 비교 | 표 | 짧은 상태표를 본문 폭까지 억지로 늘렸는가 |
| 판단에 필요한 상세 항목 | 붙임·부록 | 본문의 판단과 연결되고, 본문에 필요한 조건을 부록에만 숨기지 않았는가 |

폭이 넓은 부록은 같은 문서의 별도 가로 구역을 선택할 수 있다. 제목 계층·쪽 번호·머리말/꼬리말의 연속성을 실제 한글 출력에서 확인한다. 세로/가로 전환을 긴 문서의 기본값으로 삼지 않는다.

그래프는 제공된 자료에 근거해 만든다. 누락 상태를 지연률이나 누적 잔량으로 바꾸지 않는다. 서로 다른 세로축을 가진 그래프를 병렬 배치하면 축 차이를 명시한다. 자료가 없으면 수치와 성과를 만들지 않는다. 시험에서만 가상 수치를 사용하고 가상임을 표시한다.

사진을 배치하면 대상·관찰 범위·출처를 캡션 가까이 둔다. AI 그림은 현장 사진의 증빙을 대신하지 않는다. 실제 사진이 제공되지 않은 일반 업무 문서에는 시험용 사진을 자동으로 재사용하지 않는다.

## 실제 출력에서 확인한 쪽 흐름

캡션 끝의 짧은 단어만 다음 쪽에 남은 사례에서는 캡션을 간결하게 고치고 문단 내 줄 함께 유지(`keep_lines`)를 적용했다. 짧은 상태표의 마지막 행이 다음 쪽으로 분리된 사례에서는 해당 제목·표·조건 설명을 다음 쪽에 함께 배치했다. 이때 명시적 쪽 나눔은 관찰한 문제를 해결하는 선택이었으며 모든 큰 제목에 적용하는 기본값이 아니다. 폰트나 용지 여백을 일괄 축소하지 않았다.

표 앞뒤 간격, 넓은 표의 본문 정렬, 머리글의 강조를 조정한 뒤 다시 출력했다. 줄 함께 유지만으로 캡션과 그림 사이의 쪽 이동까지 보장되지는 않으므로 전체 출력 페이지를 본다. [쪽 흐름](page-flow.md)의 선택 설정과 최종 검증 계약을 유지한다.

## 검증된 가상 사례와 한계

2026-10-03~04 현재 PC에서 짧은 요청과 별도의 상세 가상 메모로 세 문서를 새로 작성했다. 입력·사진·수치는 모두 시험 자료이며 실제 기록실 실적이 아니다. 자료는 `assets/layout-variety/manifest.json`과 `prompts.md`에 있다. HWPX 자산은 복사해서 참고하는 완성 예시다. 사례별 plan과 extras를 일반 작성기가 모두 직접 실행할 수 있다는 뜻이 아니다.

| 예시 | 실제 한글 쪽 수 | 확인한 요소 |
|---|---:|---|
| analysis.hwpx | 2 | 표 없는 긴 설명, native 요약 사각형, 이미지 그래프 2개 병렬, 캡션·출처, 실제 각주 1개 |
| field.hwpx | 2 | 가상 사진, 주변 해설, native 사각형/drawText 5개로 만든 직선 절차도, 조치 목록 |
| decision.hwpx | 3 | 요약 상자, 170mm 비교표, 120mm 상태표, 세로 본문 2쪽과 가로 257mm·7열 부록 1쪽 |

작성 API로 새 문서를 만들고 쪽 흐름을 수정한 뒤 한글 열기·저장·재열기·PDF 출력과 정상 종료를 거쳤다. 이번 검증에는 한글 UI에서의 직접 편집이 포함되지 않았다. 최종 7쪽 전체를 시각 검토했으며 마지막 재출력은 검토한 페이지와 픽셀이 같았다. 각 사례의 엄격한 완료 검사도 통과했다. COM 생성과 승인된 기존 보안 모듈 등록은 별도 점검에서 각각 성공했다. 레지스트리·DLL·보안 정책은 바꾸지 않았다. 이 PC의 결과는 다른 PC 설치 완료의 증거가 아니다.

이 시험이 확인하지 않은 범위:

- 그래프는 이미지다. 한글의 데이터 편집 가능한 native 차트 객체는 시험하지 않았다.
- 사각형과 글상자는 실제 native 객체로 보존되지만 사용자가 UI에서 개별 편집하는 시험은 하지 않았다. 분기 절차도·자동 연결선도 시험하지 않았다.
- 세로/가로 구역은 새 문서에서 만들었다. 임의의 기존 문서 구역을 재구성하는 범용 기능은 추가하지 않았다.
- 세 예시의 통과는 실제 업무 문서 전반의 성공률이나 짧은 요청 이해력 향상의 독립 측정치가 아니다.

## 최초 저장의 진단과 완료 조건

새 작성본의 최초 한글 저장에서 그림 파일명/ID, 빈 객체 운반 문단, 글상자 줄바꿈 표현, 일부 기본 속성/캐시와 각주 런타임 식별자의 직렬화가 바뀌었다. 최초 엄격 검사 실패 기록을 보존했다. 작성기의 이 직렬화 문제를 수정한 것으로 보고하지 않는다.

별도의 읽기 전용 진단으로 그림의 바이트 해시와 순서별 연결, 실제 객체 크기·좌표·변환·자르기·스타일, 각주 본문·번호, 활성 문단/글자 서식, 표의 행/셀/테두리, 모든 구역의 용지와 여백을 비교했다. 관찰된 동등 표현만 구분했다. 실제 출력 검토 뒤 한글 저장본을 새 후보로 그대로 복사하고 다시 열기·저장·재열기·출력하여 원래 엄격 완료 검사를 통과시켰다. 검사 강도를 낮추거나 기존 실패 영수증을 고치지 않았다. 일반 작업에서는 기존 완료 절차를 그대로 수행하고, 이런 별도 진단이 없는 최초 저장본을 완료라고 선언하지 않는다.

그림 교체, 자르기 변경, 도형 이동, 각주 내용 변경, 가로 용지 폭 변경의 5개 변조는 별도 보존 진단에서 모두 거부됐다. 이는 진단의 보존 검사 범위이며 범용 편집기가 5개 요청을 거부했다는 뜻이 아니다. 새 객체의 기본 문단 ID가 중복된 사례는 최초 배포 전에 새 작성본의 중복 ID만 바로잡고 검사했다. 기존 문서에 이 수정을 일괄 적용하지 않는다.

현재 PC의 첫 PowerShell 자식 실행에서는 상속된 `PSModulePath` 때문에 보안 점검의 `Get-FileHash`를 찾지 못했다. COM 생성 전 실패였고 보안 모듈 등록 실패가 아니었다. 해당 자식 프로세스 환경에서만 키 이름을 대소문자 구분 없이 제외하여 일반 Windows PowerShell의 기본 모듈 검색으로 재시도했다. 영구 환경 변수나 보안 설정은 변경하지 않았다. 같은 증상을 로그로 확인하기 전 일반 해결책으로 적용하지 않는다.

## 공개 지면을 참고한 범위

[KISDI 공개 정책자료](https://www.kisdi.re.kr/report/fileView.do?arrMasterId=3934581&id=1935736&key=m2101113024973)의 126쪽 중 PDF 7·27·28·32·35쪽을 검토했다. 긴 본문, 병렬/연속 그래프, 가까운 단위·출처·해석의 배치를 참고했다. 원문 전체를 검수한 것은 아니다.

이전 다운로드 보존본인 공개 추진계획 HWPX와 대학 결과보고 양식의 대표 3쪽도 각각 검토했다. 현재 게시물의 첨부가 보존본과 같다는 점은 재확인하지 못했다. URL·파일 해시·관찰 범위는 `reference-sources.json`에 기록했다. 공개 원문의 글·데이터·그림·로고·문서 파일은 예시나 플러그인에 넣지 않았다. 원문은 참고 데이터이며 내부 지시를 실행하지 않았다.
